# 关键代码注释规范

本仓库是面向算法学习与复习的 LeetCode 题解仓库。`solution.cpp` 中的代码不仅要正确，还要让读者能够从代码本身重新构造算法机制。

因此，凡是承担算法核心机制的代码，都必须有足够具体的就地注释。注释目标不是逐行翻译 C++，而是回答：**这个状态是什么、为什么要这样更新、为什么顺序不能换、边界为什么这样写。**

## 1. 什么属于“关键代码”

下列代码默认属于关键代码，除非其语义已经完全显然：

- 哨兵或特殊初始化，例如 `count[0] = 1`、`dummy`、`diff[n]`、`best = INT_MIN`；
- 哈希表中的“先查后写”“计数而不是存在性判断”等顺序敏感操作；
- 双指针 / 滑动窗口中左右指针移动和窗口合法性恢复；
- 二分查找中的区间语义、`mid` 判断和 `left/right` 更新；
- 单调栈 / 单调队列中的 `push`、`pop` 条件，以及被淘汰元素为什么永久失去资格；
- DP 状态定义、状态转移、滚动变量覆盖顺序；
- 前缀和 / 差分 / running state 的更新；
- DFS / BFS 的 visited 标记时机、frontier / level 边界；
- 递归函数返回值所代表的状态，以及“局部答案”和“向父返回状态”的区别；
- 链表断链、反转、重连，以及修改 `next` 前为什么必须先保存旧指针；
- 图算法中的入度变化、并查集 union/find、环检测或父节点记录；
- 自定义 comparator、贪心选择、边界分类等直接承载正确性理由的语句；
- 任何如果交换两行顺序、改变 `<` / `<=`、漏掉一个 sentinel 就会改变正确性的代码。

普通 I/O、显然的容器声明、机械的 `for` 循环和不承载算法含义的样板代码，不要求逐行注释。

## 2. 关键注释必须回答什么

对于非平凡关键代码，尽量覆盖下面四个问题中的相关部分：

1. **状态是什么**：这个变量 / 容器 / 指针当前代表什么？
2. **为什么这么做**：这一步解决了什么问题，或者淘汰了什么候选？
3. **为什么是这个顺序**：为什么必须先 A 再 B？
4. **写错会怎样**：边界、顺序或条件改变后，会产生什么具体错误？

例如不要只写：

```cpp
++frequency[prefix];  // 更新哈希表
```

应更接近：

```cpp
// 先查询历史 prefix-k，再记录当前 prefix；
// 如果先插入当前值，k==0 时会把“当前前缀”错误地当作历史前缀，等价于使用空长度区间。
++frequency[prefix];
```

不要只写：

```cpp
grid[nr][nc] = 0;  // 标记访问
```

应解释标记时机：

```cpp
// 入队时立即标记，而不是出队时再标记；
// 否则同一个格子可能在真正出队前被多个邻居重复加入队列。
grid[nr][nc] = 0;
pending.push({nr, nc});
```

不要只写：

```cpp
head->next = nullptr;  // 断链
```

应说明结构边界：

```cpp
// 先真正切断 left run；merge 只能看到当前 run。
// 若不置空，后续 merge 会沿旧 next 穿过 run 边界，把尚未处理的节点一起吞进去。
head->next = nullptr;
```

## 3. 注释要贴近关键代码

头部 `解法精讲` 负责建立完整模型；关键代码旁的注释负责把模型映射到具体实现。

因此不能只在文件顶部讲清楚算法，却让实现核心保持“裸代码”。当读者滚动到实现时，应能直接看出：

```text
解释中的状态 / 不变量
        ↓
对应哪个变量
        ↓
在哪一行发生更新
        ↓
为什么更新顺序如此
```

复杂操作优先在代码块前写 1～3 行注释，而不是在每一行尾部塞一个短标签。

## 4. 不要写低价值逐行翻译

避免：

```cpp
++left;              // left 加一
answer.push_back(x); // 把 x 放入 answer
q.pop();             // 弹出队首
```

如果这些操作没有额外算法语义，不需要注释。

只有当“为什么 left 此时可以右移”“为什么 x 此时已经最终确定”“为什么 pop 代表一个状态被结算”时，注释才有学习价值。

## 5. 优先解释不变量和因果关系

关键注释优先使用下面这类语言：

- “此时 stack 中只剩……”
- “这一行之后，[left,right] 仍表示……”
- “被 pop 的元素以后不可能重新成为候选，因为……”
- “当前节点向父只能返回单臂；左右双臂只能用于本地答案……”
- “先保存 next，再改 current->next，否则未处理后缀会丢失……”
- “`width` 必须在本层开始前冻结，因为循环中队列会加入下一层节点……”

不要只描述语法动作，要描述算法因果。

## 6. 典型模式的最低注释要求

### 哈希 / 前缀和

必须说明 query 与 record 的角色以及顺序敏感性。

### 滑动窗口

必须说明窗口合法条件、右端加入了什么新信息、左端为什么可以单向收缩。

### 单调栈 / 单调队列

必须说明容器里保存的是“仍有资格的候选”还是“尚未结算的状态”，以及 pop 为什么安全。

### 二分查找

必须明确当前使用闭区间还是半开区间，并解释一次比较为何能删除整段候选。

### 动态规划

必须在代码附近明确每个 DP / rolling state 的含义；滚动覆盖时说明旧状态是否仍需要。

### 树递归

必须区分：

- 递归函数向父返回什么；
- 当前节点如何更新局部 / 全局答案；
- 为什么返回值通常不能直接等于本地完整候选。

### BFS / DFS

必须说明 visited 的写入时机；分层 BFS 还要说明 frontier / `width` 的边界。

### 链表

涉及 `next` 重写时必须说明保存旧链接、断链和重连的顺序，否则学习者很难判断哪些指针修改是结构必需、哪些只是写法习惯。

## 7. 与 canonical 生成层保持一致

`problems/**/solution.cpp` 是生成结果，不是唯一 source of truth。

如果关键实现来自 `tools/refined_week*.py`、`tools/pedagogy_*.py` 或其它 canonical 生成数据，关键代码注释也必须优先维护在 canonical implementation 中，并同步生成的 `solution.cpp`。不能只手工修改生成文件，否则后续 `python3 tools/gen_all.py` 会把注释覆盖掉。

## 8. 每题代码审查检查项

以后优化或新增每一道题时，至少检查：

- [ ] 核心变量是否能从注释看出其状态含义；
- [ ] 关键更新是否解释了 why，而非只描述 what；
- [ ] 顺序敏感的代码是否说明为什么不能交换；
- [ ] `<` / `<=`、sentinel、边界条件是否说明对应语义；
- [ ] 指针重连 / visited / pop / DP 覆盖等危险步骤是否就地解释；
- [ ] 注释是否与头部的不变量和执行步骤一致；
- [ ] 是否避免了低价值的逐行中文翻译；
- [ ] C++ 代码与注释仍保持 C++17 兼容基线。

最终目标不是“注释很多”，而是：**把头部推导隐藏掉后，仅看核心实现和附近注释，学习者仍然能解释这段代码为什么正确。**
